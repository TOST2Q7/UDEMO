# 09. ГОСТ-сертификаты — `gost.sh`, `gost-isp.sh`, `gost-hqcli.sh`

**Задача этапа.** Перевести веб-сервисы `web.au-team.irpo` и
`docker.au-team.irpo` на **HTTPS с сертификатами на российских
криптоалгоритмах** (ГОСТ Р 34.10-2012 — подпись, ГОСТ Р 34.11-2012
«Стрибог» — хэш) и добиться, чтобы браузер на HQ-CLI открывал их **без
предупреждений**.

Для этого нужны три участника — отсюда три скрипта:

```
 HQ-SRV  gost.sh        ── создаёт свой УЦ, выпускает сертификаты
            │ scp (root@172.16.1.1)            │ scp -P 2027 (sshuser@HQ-CLI)
            ▼                                  ▼
 ISP     gost-isp.sh    ── nginx: HTTPS       HQ-CLI  gost-hqcli.sh ── доверяет УЦ
         (ключи + сертификаты сайтов)                 (только корневой ca.cer)
```

Принцип разделения — **каждому узлу только то, что ему нужно**:

* **закрытый ключ УЦ** (`ca.key`) никогда не покидает HQ-SRV;
* ISP получает ключи и сертификаты **сайтов** — он их обслуживает;
* HQ-CLI получает только **публичный** корневой сертификат — ему нужно
  лишь проверять подписи.

---

## Часть 1. `gost.sh` (HQ-SRV) — удостоверяющий центр

### 1.1. Переменные

| Переменная | Значение | Смысл |
|---|---|---|
| `CA_DIR` | `$DIR/gost-ca` | вся «кухня» УЦ в одном каталоге рядом со скриптом; `delete` удаляет его целиком |
| `DAYS=30` | срок действия | короткий срок достаточен для стенда и не создаёт иллюзии «боевого» УЦ |
| `CA_SUBJ` | `/C=RU/ST=Krasnoyarsk/O=AU-TEAM/CN=AU-TEAM Root CA` | имя УЦ: страна, регион, организация, общее имя. CN — то, что видно в браузере в цепочке |
| `WEB_FQDN`, `DOCKER_FQDN` | имена сайтов | должны совпадать с тем, что пользователь вводит в адресной строке |
| `ISP_USER=root`, `ISP_HOST=172.16.1.1` | куда доставлять сертификаты сайтов | ISP со стороны HQ; root разрешён специально для этого (см. [02-isp.md §7](02-isp.md#8-ssh-разрешён-вход-root)) |
| `HQCLI_USER=sshuser`, `HQCLI_PORT=2027` | куда доставлять ca.cer | единственный пользователь с SSH на HQ-CLI |
| `HQCLI_SUBNET`, `HQCLI_POOL` | `192.168.200`, `2..10` | DHCP-пул для поиска HQ-CLI |
| `HQCLI_HOST="${HQCLI_HOST:-}"` | пусто или из окружения | `HQCLI_HOST=1.2.3.4 ./gost.sh` пропускает поиск |

### 1.2. Включение ГОСТ в OpenSSL

```bash
apt-get install -y openssl-gost-engine
control openssl-gost enabled
if ! openssl genpkey -algorithm gost2012_256 -pkeyopt paramset:A -out /dev/null 2>/dev/null; then
    echo "GOST engine is not active, aborting" >&2
    exit 1
fi
```

* Штатный OpenSSL ГОСТ не знает. Алгоритмы добавляет **engine** (модуль)
  `gost` из пакета `openssl-gost-engine`.
* Установить engine мало — его надо **подключить** в конфиге OpenSSL. В ALT
  это делается через `control openssl-gost enabled`, который правит
  системный `openssl.cnf` за вас.
* Пробная генерация ключа в `/dev/null` — **fail fast**: если engine не
  заработал, дальнейшие команды выпускали бы ошибки одна за другой. Лучше
  сразу остановиться с понятным сообщением. Это одно из немногих мест с
  `exit 1` — без ГОСТ продолжать бессмысленно.

### 1.3. Корневой сертификат УЦ

```bash
openssl genpkey -algorithm gost2012_256 -pkeyopt paramset:TCB -out "$CA_KEY"
openssl req -new -x509 -md_gost12_256 -days "$DAYS" -key "$CA_KEY" -subj "$CA_SUBJ" -out "$CA_CER"
chmod 600 "$CA_KEY"
```

* `gost2012_256` — ключ ГОСТ Р 34.10-2012 длиной 256 бит.
* `paramset:TCB` / `paramset:A` — наборы параметров эллиптической кривой
  (`TCB` — набор ТК 26, `A` — набор CryptoPro-A). Оба стандартные и
  поддерживаются engine; явное указание нужно, потому что без него
  `genpkey` для ГОСТ-ключа не знает, какую кривую взять, и завершится
  ошибкой. Почему для УЦ и сайтов выбраны разные наборы, в коде не
  объяснено — криптографически это не обязательно.
* `req -new -x509` — сразу **самоподписанный** сертификат (а не запрос):
  корневой УЦ подписывает себя сам, выше него доверять некому.
* `-md_gost12_256` — хэш «Стрибог-256» для подписи.
* `-subj` — имя без интерактивных вопросов.
* `chmod 600` — закрытый ключ читает только root. Кто владеет `ca.key`,
  может выпустить «доверенный» сертификат на любое имя.

### 1.4. Ключи и запросы (CSR) для сайтов

```bash
openssl genpkey -algorithm gost2012_256 -pkeyopt paramset:A -out "$WEB_FQDN.key"
openssl req -new -md_gost12_256 -key "$WEB_FQDN.key" \
    -subj "/C=RU/O=AU-TEAM/CN=$WEB_FQDN" \
    -addext "subjectAltName=DNS:$WEB_FQDN" \
    -out "$WEB_FQDN.csr"
```

У каждого сайта **свой** ключ: компрометация одного не затрагивает другой.

**Почему `subjectAltName`, если имя уже есть в CN.** Современные браузеры
на движке Chromium (в том числе Яндекс Браузер) **игнорируют CN** и
сверяют имя сайта только с расширением SAN. Без SAN сертификат будет
отвергнут с ошибкой «имя не совпадает», даже если CN верный (комментарий в
скрипте говорит именно об этом).

### 1.5. Подпись сертификатов сайтов

```bash
printf 'subjectAltName=DNS:%s\n' "$WEB_FQDN" > "$WEB_FQDN.extfile"
openssl x509 -req -in "$WEB_FQDN.csr" -CA "$CA_CER" -CAkey "$CA_KEY" -CAcreateserial \
    -md_gost12_256 -days "$DAYS" -extfile "$WEB_FQDN.extfile" \
    -out "$WEB_FQDN.cer"
```

* `x509 -req` — подписать CSR ключом УЦ, получив сертификат.
* **Почему отдельный `extfile`.** `openssl x509 -req` **не копирует
  расширения из CSR** — SAN, заботливо положенный в запрос, при подписи
  потерялся бы. В OpenSSL 3.0+ есть ключ `-copy_extensions`, но в
  OpenSSL 1.1.1 его нет — и скрипт на нём падал (коммит `3e2e8f4`).
  `-extfile` с тем же SAN работает одинаково на обеих версиях.
* `-CAcreateserial` — создать файл `ca.srl` с серийным номером; каждый
  сертификат одного УЦ должен иметь уникальный серийник.
* Расширение `.cer` вместо `.crt`/`.pem` — просто соглашение; формат внутри
  — PEM.

### 1.6. DNS

Тот же блок, что в `hq-srv.sh` (`127.0.0.1`, `chattr -i`, копия в
`enp7s1.100`). Повторён здесь, чтобы `gost.sh` оставлял систему в
корректном состоянии, даже если `hq-srv.sh` был запущен в старой версии.

### 1.7. Проверки до доставки

Помимо «файл существует»:

* `openssl verify -CAfile ca.cer ca.cer` — корневой сертификат корректно
  самоподписан;
* `openssl verify -CAfile ca.cer web….cer` — сертификат сайта **действительно
  подписан нашим УЦ** и цепочка сходится;
* `openssl x509 -text | grep DNS:…` — SAN на месте (защита от ошибки из
  §1.5).

### 1.8. Доставка

```bash
for f in …; do [ ! -s "$CA_DIR/$f" ] && { echo "…"; exit 1; }; done
```

**Не копировать ничего, если хоть один файл не создан** — иначе на ISP
могли бы оказаться ключ без сертификата или старый сертификат с новым
ключом, и nginx упал бы с непонятной ошибкой.

**Пакет `sshpass`** ставится вместе с ГОСТ-движком: он будет вводить
пароль стенда за пользователя.

**Функция `copy_files`:**

```bash
SSH_OPTS=(-o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null -o ConnectTimeout=5)

copy_files() {
    local port="$1" dest="$2" rc=1; shift 2
    if command -v sshpass >/dev/null; then
        sshpass -p "$SSH_PASSWORD" scp -P "$port" "${SSH_OPTS[@]}" "$@" "$dest:~/"
        rc=$?
        [ "$rc" = 0 ] && return 0
        case "$rc" in
            5) echo "… rejected password …" ;;
            *) echo "… sshd refused or closed the connection" ;;
        esac
    fi
    if [ -r /dev/tty ]; then
        scp -P "$port" "${SSH_OPTS[@]}" "$@" "$dest:~/" </dev/tty && return 0
    fi
    return 1
}
```

Одна функция для обеих доставок (ISP и HQ-CLI) — различаются только
порт, адресат и список файлов.

| Элемент | Зачем |
|---|---|
| `SSH_OPTS` как **массив** | каждая опция остаётся отдельным аргументом при подстановке `"${SSH_OPTS[@]}"` — строка с пробелами развалилась бы или склеилась |
| `StrictHostKeyChecking=no` | не спрашивать `yes/no` про неизвестный ключ хоста: `sshpass` на этот вопрос ответить не умеет, и копирование бы зависло/упало |
| `UserKnownHostsFile=/dev/null` | не запоминать ключи. После переустановки ВМ ключ хоста меняется, и сохранённый старый ключ вызвал бы жёсткую ошибку «REMOTE HOST IDENTIFICATION HAS CHANGED» |
| `ConnectTimeout=5` | не висеть минутами, если узел недоступен |
| `sshpass -p` | ввести пароль `P@ssw0rd` автоматически — все учётки стенда используют его |
| код возврата `5` | так `sshpass` сообщает «пароль неверен» — выводится понятная причина вместо общего «не получилось» |
| повтор без `sshpass` через `/dev/tty` | если автоматический вход не удался (пароль изменён, `sshpass` не установился) — второй шанс ввести пароль руками. `/dev/tty` — прямой ввод с терминала, работает, даже если сам скрипт запущен через конвейер (`wget -O- … \| bash`), где stdin занят |

**На ISP:** `copy_files 22 root@172.16.1.1 <4 файла>` — ключи и
сертификаты сайтов в `~root`. Порт 22: на ISP SSH на стандартном порту.
При неудаче NEXT STEP подсказывает, что проверить на ISP
(`PermitRootLogin yes`, журнал `sshd`) — это самая частая причина, по
которой ISP «закрывает соединение сразу после пароля».

**Поиск HQ-CLI** — параллельно по всему пулу:

```bash
port_open() { timeout 3 bash -c "</dev/tcp/$1/$2" 2>/dev/null; }

SCAN_DIR="$(mktemp -d)"
for i in $HQCLI_POOL; do
    (
        ip="$HQCLI_SUBNET.$i"
        if port_open "$ip" "$HQCLI_PORT"; then echo open > "$SCAN_DIR/$ip"
        elif ping -c 1 -W 2 "$ip" &>/dev/null; then echo closed > "$SCAN_DIR/$ip"
        fi
    ) &
done
wait
```

* **Параллельно** (`( … ) &` + `wait`): девять адресов проверяются
  одновременно, и весь поиск занимает ~3 секунды, а не до 9 × 3.
* **Результаты — через файлы во временном каталоге**: фоновые подпроцессы
  не могут менять переменные родителя, поэтому каждый пишет свой вердикт в
  файл `$SCAN_DIR/<ip>`, а родитель после `wait` их читает.
* **Сначала порт, потом ping**: порт проверяется первым, потому что ICMP
  может быть заблокирован, а TCP-проверка — именно то, что нужно для `scp`.
  Ping нужен только для диагностики: отличить «узел есть, но SSH на 2027 не
  слушает» (подсказка: `ss -tlnp | grep 2027` на HQ-CLI) от «узла нет».
* `/dev/tcp` вместо `nc` — netcat в ALT по умолчанию не установлен.
* Если найдено несколько адресов с открытым портом, берётся первый, но
  выводятся все — видно, если в VLAN 200 оказалось несколько клиентов.

**Если автоматически не нашли** — скрипт не сдаётся, а спрашивает адрес:

```bash
read -rp "HQ-CLI address (Enter to skip): " HQCLI_HOST </dev/tty
```

и предупреждает, если на введённом адресе порт 2027 закрыт. Enter —
пропустить доставку на HQ-CLI (ISP при этом уже обслужен).

**На HQ-CLI:** `copy_files 2027 sshuser@<адрес> ca.cer` — только корневой
сертификат, в домашний каталог `sshuser` (root по SSH на HQ-CLI не
пускают).

Флаги `ISP_OK`/`HQCLI_OK` фиксируют успех каждой доставки, по ним
выполняются финальные проверки и выбирается текст NEXT STEP: при неудаче
баннер печатает готовую команду для повторного копирования вручную.

## Часть 2. `gost-isp.sh` (ISP) — HTTPS в nginx

**Предпосылки.** На ISP уже работает nginx как **обратный прокси** к
веб-сервисам — его поднимает `proxy.sh`
([09-web-services.md §3](09-web-services.md#часть-3-proxysh-isp--обратный-прокси-nginx-http)),
он же создаёт файл паролей `/etc/nginx/.htpasswd`. `gost-isp.sh` лишь
переводит прокси на HTTPS, перезаписывая тот же файл виртуальных хостов.

### 2.1. Переменные

| Переменная | Значение | Смысл |
|---|---|---|
| `WEB_BACKEND` | `172.16.1.2:8080` | куда проксировать `web` — WAN-адрес HQ-RTR, порт 8080 (DNAT на HQ-SRV:80) |
| `DOCKER_BACKEND` | `172.16.2.2:8080` | куда проксировать `docker` — WAN-адрес BR-RTR (DNAT на BR-SRV:8080) |
| `SSL_DIR` | `/etc/nginx/ssl` | отдельный каталог для ключей, а не домашний каталог root |
| `VHOST` | `/etc/nginx/sites-available.d/default.conf` | конфиг виртуальных хостов nginx в раскладке ALT |
| `CERT_SRC` | `$HOME` | куда `gost.sh` положил файлы (`~root`) |

### 2.2. Проверка входных файлов

Если хоть одного из четырёх файлов нет — выход с подсказкой «сначала
`gost.sh`». Скрипт не пытается «что-нибудь настроить» без сертификатов,
чтобы не оставить nginx в сломанном состоянии.

### 2.3. ГОСТ в OpenSSL на ISP

`openssl-gost-engine` + `control openssl-gost enabled` — nginx использует
**ту же системную libssl**, поэтому, чтобы он смог загрузить ГОСТ-ключ и
вести TLS-рукопожатие на ГОСТ-алгоритмах, engine должен быть включён и
здесь.

### 2.4. Конфиг nginx

Два блока `server` — по одному на сайт; nginx выбирает нужный по имени из
TLS SNI / заголовка `Host`.

| Директива | Смысл |
|---|---|
| `listen 443 ssl` | HTTPS на стандартном порту |
| `server_name` | к какому имени относится блок |
| `ssl_certificate` / `ssl_certificate_key` | сертификат и ключ **этого** сайта |
| `proxy_pass http://…:8080` | TLS заканчивается на ISP, к бэкенду идёт обычный HTTP — бэкенды не нужно перенастраивать |
| `proxy_set_header Host $host` | бэкенд видит исходное имя сайта, а не адрес прокси |
| `X-Real-IP`, `X-Forwarded-For` | реальный IP клиента — иначе в логах бэкенда все запросы были бы «от ISP» |
| `X-Forwarded-Proto $scheme` | бэкенд знает, что исходный запрос был HTTPS (важно для генерации ссылок и редиректов) |
| `auth_basic` + `auth_basic_user_file` | **только для `web`**: базовая HTTP-аутентификация — перенесена из HTTP-конфигурации `proxy.sh`, чтобы переход на HTTPS не снял защиту |

`\$host` и т. п. экранированы в heredoc, чтобы bash не подставил свои
(пустые) переменные вместо nginx-переменных, а `$SSL_DIR`, `$WEB_FQDN`
— наоборот, намеренно подставляются.

Конфиг **полностью перезаписывается** (`cat >`), а не правится: так
результат детерминирован и не зависит от того, что было раньше.

### 2.5. Применение

```bash
nginx -t && systemctl restart nginx
```

`nginx -t` проверяет синтаксис и загружаемость ключей. Рестарт — только
при успешной проверке: при ошибке старый процесс nginx продолжит работать,
а не упадёт.

## Часть 3. `gost-hqcli.sh` (HQ-CLI) — доверие к УЦ

### 3.1. Поиск `ca.cer`

```bash
USER_HOME="$(getent passwd "$HQCLI_USER" | cut -d: -f6)"
for c in "$USER_HOME/ca.cer" "$HOME/ca.cer" "$DIR/ca.cer"; do …
```

`gost.sh` кладёт файл в домашний каталог `sshuser`, а этот скрипт обычно
запускают от root (у которого `$HOME=/root`). Поэтому путь к дому
`sshuser` вычисляется из базы пользователей (`getent passwd`, 6-е поле), а
на случай ручного копирования проверяются ещё `$HOME` и каталог скрипта
(коммит `ae00348`).

### 3.2. Установка в системное хранилище

```bash
cp "$CA_CER" /etc/pki/ca-trust/source/anchors/ca.cer
update-ca-trust
```

* `/etc/pki/ca-trust/source/anchors/` — каталог «якорей доверия»,
  добавленных администратором.
* `update-ca-trust` пересобирает общесистемные хранилища сертификатов
  (PEM-бандлы, хранилище p11-kit), которыми пользуются OpenSSL, curl,
  wget и браузеры, подключённые к системному хранилищу.

После этого любая программа на HQ-CLI, проверяющая сертификат сайта,
найдёт в цепочке доверенный корень `AU-TEAM Root CA`.

### 3.3. `/etc/hosts`

```bash
for fqdn in "$WEB_FQDN" "$DOCKER_FQDN"; do
    sed -i "/[[:space:]]${fqdn//./\\.}\([[:space:]]\|\$\)/d" /etc/hosts
    echo "$PROXY_IP $fqdn" >> /etc/hosts
done
```

**Зачем.** В `dnsmasq.conf` на HQ-SRV нет записей для `web` и `docker`, а
обращаться к ним надо по имени (иначе не совпадёт SAN сертификата). Имена
указываются на `172.16.1.1` — адрес nginx на ISP, доступный из офиса
через HQ-RTR.

**Как сделана идемпотентность.** Перед добавлением удаляются **все**
прежние строки с этим именем, поэтому повторный запуск не плодит дубли.
`${fqdn//./\\.}` экранирует точки для regex; шаблон требует пробельный
символ перед именем и пробел или конец строки после — чтобы не задеть,
например, `myweb.au-team.irpo.old`.

### 3.4. Проверки

| Проверка | Смысл |
|---|---|
| anchor существует | сертификат положен |
| `cmp -s` anchor и исходный файл | положен **тот самый** сертификат, а не устаревший |
| `update-ca-trust` доступен | системная утилита на месте |
| `getent hosts web…` = `172.16.1.1` | имя разрешается туда, где nginx |

Итоговая проверка — вручную: `https://web.au-team.irpo` и
`https://docker.au-team.irpo` в браузере HQ-CLI должны открыться без
предупреждения о сертификате.
