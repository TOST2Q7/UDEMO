# 00. Обзор стенда: что строится и почему именно так

Этот документ — не инструкция «что нажать», а объяснение устройства всей ветки
`checks`. Здесь описано, **какую сеть собирают скрипты**, **зачем она так
разбита на сегменты**, **в каком порядке всё поднимается и почему порядок
именно такой**, а также сквозные решения, которые повторяются во всех файлах.
Разбор каждого скрипта построчно — в следующих документах (см. [readme](../readme.md)).

---

## 1. Что это вообще за проект

Ветка содержит набор bash-скриптов, которые «с нуля» настраивают учебный стенд
из семи виртуальных машин под управлением **ALT Linux** (серверные/JeOS-образы
и рабочая станция). Стенд имитирует небольшую компанию:

* **головной офис (HQ)** — маршрутизатор, сервер, клиентская машина;
* **филиал (BR, branch)** — маршрутизатор и сервер;
* **провайдер (ISP)** — машина, через которую офисы выходят в интернет и
  связываются друг с другом; она же — сервер точного времени и обратный
  прокси для веб-сервисов компании.

Все имена узлов живут в DNS-домене **`tkhis.pro`**, а на BR-SRV
поднимается домен Active Directory **`TKHIS.PRO`** (Samba).

Набор задач (VLAN, GRE, OSPF, DHCP, DNS, NTP, RAID, NFS, SSH на нестандартном
порту, Samba AD, Ansible, веб-сайт на LAMP, Docker, обратный прокси nginx,
ГОСТ-сертификаты) типичен для демонстрационного
экзамена по сетевому и системному администрированию, поэтому многие «странные»
значения (порт `2027`, пароль `P@ssw0rd`, UID `2027`, баннер
`Authorized access only`) — это не выбор автора, а требования задания. В
документах такие места помечены как **«требование задания»**, чтобы было
видно, где решение принималось, а где просто исполнялось.

## 2. Топология

```
                          Интернет
                              │  (DHCP от вышестоящей сети)
                           enp7s1
                      ┌───────────────┐
                      │      ISP      │  NAT (MASQUERADE) наружу, NTP (chrony),
                      │ isp.tkhis.pro │  nginx reverse-proxy (HTTP → HTTPS/ГОСТ)
                      └──┬─────────┬──┘
              enp7s2     │         │     enp7s3
         172.16.1.1/28   │         │   172.16.2.1/28
                         │         │
         172.16.1.2/28   │         │   172.16.2.2/28
                  enp7s1 │         │ enp7s1
              ┌──────────┴──┐   ┌──┴──────────┐
              │   HQ-RTR    │   │   BR-RTR    │
              │  tun0 ══════GRE═══════ tun0   │   10.10.10.0/24
              │ 10.10.10.1  │   │ 10.10.10.2  │   (OSPF area 0, MD5)
              └──────┬──────┘   └──────┬──────┘
                enp7s2 (trunk)     enp7s2 192.168.0.1/28
         ┌───────────┼───────────┐     │
     VLAN 100    VLAN 200    VLAN 999  │  192.168.0.0/28
  192.168.100.1 192.168.200.1 192.168.99.1
       /28          /29          /29   │
         │            │                │
     ┌───┴───┐    ┌───┴───┐        ┌───┴───┐
     │HQ-SRV │    │HQ-CLI │        │BR-SRV │
     │ .100.2│    │ DHCP  │        │ .0.2  │
     └───────┘    └───────┘        └───────┘
   DNS (dnsmasq)  Браузер,        SSH, Ansible,
   RAID5 + NFS    NFS-клиент      Samba AD DC,
   сайт (LAMP)                    Docker (testapp)
   ГОСТ-УЦ
```

### Почему сеть разбита именно так

* **ISP отделён от офисов двумя разными подсетями** (`172.16.1.0/28` и
  `172.16.2.0/28`). Так имитируется реальность: у каждого офиса свой канал к
  провайдеру, и офисы не видят друг друга напрямую — только через «интернет».
  Именно поэтому между маршрутизаторами нужен туннель.
* **GRE-туннель `10.10.10.0/24`** соединяет HQ-RTR и BR-RTR поверх
  провайдерской сети. Через него частные сети офисов (`192.168.x.x`) могут
  маршрутизироваться друг к другу, хотя провайдер о них ничего не знает.
  Маска `/24` — из 254 адресов заняты только два, по одному на каждый конец
  соединения «точка-точка».
* **OSPF поверх туннеля** избавляет от ручного прописывания маршрутов: каждый
  маршрутизатор сам сообщает соседу, какие сети за ним находятся.
* **В головном офисе три VLAN на одном физическом порту** (trunk на `enp7s2`
  HQ-RTR): серверы (100), клиенты (200), управление (999). Это разделение по
  назначению: у каждой группы своя подсеть, свой широковещательный домен и
  возможность разных правил доступа. В филиале всего один сервер, поэтому там
  «плоская» сеть без VLAN.
* **В филиале BR-SRV подключён к BR-RTR напрямую**: `enp7s2` BR-RTR —
  шлюз сети филиала `192.168.0.1`, у него же внешний адрес, NAT и проброс
  портов на BR-SRV.

### Адресный план

| Сегмент | Сеть | Шлюз | Узлы | Почему такая маска |
|---|---|---|---|---|
| ISP ↔ HQ-RTR | 172.16.1.0/28 | 172.16.1.1 (ISP) | HQ-RTR .2 | /28 = 14 адресов, требование задания |
| ISP ↔ BR-RTR | 172.16.2.0/28 | 172.16.2.1 (ISP) | BR-RTR .2 | то же |
| GRE-туннель | 10.10.10.0/24 | — | HQ-RTR .1, BR-RTR .2 | точка-точка, используются 2 адреса из 254 |
| HQ VLAN 100 (серверы) | 192.168.100.0/28 | 192.168.100.1 | HQ-SRV .2 | 16 адресов, до 14 узлов |
| HQ VLAN 200 (клиенты) | 192.168.200.0/29 | 192.168.200.1 | HQ-CLI из пула .2–.6 | 8 адресов, до 6 узлов, адреса по DHCP |
| HQ VLAN 999 (управление) | 192.168.99.0/29 | 192.168.99.1 | — | 8 адресов, до 6 узлов |
| BR LAN | 192.168.0.0/28 | 192.168.0.1 (BR-RTR) | BR-SRV .2 | до 14 узлов |

Размеры подсетей подобраны «впритык» под требуемое количество узлов из
задания — это стандартная учебная практика экономии адресного пространства.

## 3. Порядок запуска и почему он такой

```
 1. ISP        isp.sh          ← без него ни у кого нет интернета; заодно сервер времени
 2. HQ-RTR     hq-rtr.sh       ┐ оба зависят только от ISP;
 3. BR-RTR     br-rtr.sh       ┘ туннель поднимется, когда готовы оба
 4. HQ-SRV     hq-srv.sh       ← DNS-сервер всего стенда
 5. HQ-RTR     hq-rtr-2.sh     ← только теперь есть куда направить DHCP-клиентов за DNS
 6. HQ-CLI     hq-cli.sh       ← нужен NFS с HQ-SRV и DNS
 7. BR-SRV     br-srv.sh       ← Ansible опрашивает все предыдущие узлы
 8. BR-SRV     samba.sh        ← контроллер домена, форвардит DNS на HQ-SRV
 9. HQ-SRV     web.sh          ┐ бэкенды веб-сервисов (нужен ISO задания в /dev/sr0),
10. BR-SRV     docker.sh       ┘ в любом порядке
11. ISP        proxy.sh        ← обратный прокси: проверяет оба бэкенда вживую
12. HQ-SRV     gost.sh         ← УЦ, раздаёт сертификаты на ISP и HQ-CLI
13. ISP        gost-isp.sh     ← переводит прокси на HTTPS
14. HQ-CLI     gost-hqcli.sh   ← доверяет корневому сертификату
    BR-SRV     get_hostname.yml (ansible-playbook, в любой момент после 7)
    BR-SRV     samba-users.sh  (импорт пользователей из Users.csv, после 8)
    HQ-SRV     fail2ban.sh, cups.sh (защита SSH и принт-сервер, после 4)
    по заданию atop.sh         (мониторинг)
```

Логика порядка — **зависимости по сети и сервисам**:

* Каждому скрипту нужен интернет (`apt-get`, `wget`), а интернет идёт через
  ISP → поэтому ISP первым.
* Маршрутизаторы — до серверов, потому что серверы ходят в интернет через них.
* DHCP на HQ-RTR сначала раздаёт клиентам **публичный** DNS `77.88.8.8`
  (своего ещё нет), а после появления DNS на HQ-SRV отдельный маленький скрипт
  `hq-rtr-2.sh` переключает его на `192.168.100.2`. Это причина, по которой
  настройка HQ-RTR разрезана на две части.
* HQ-CLI монтирует NFS с HQ-SRV → HQ-SRV должен быть готов раньше.
* BR-SRV в конце своего скрипта прозванивает Ansible-ом все узлы → они должны
  уже существовать.
* Прокси на ISP — после обоих бэкендов: его проверки делают настоящие
  HTTP-запросы к сайтам и без бэкендов получили бы 502.
* ГОСТ-сертификаты — последний этап, потому что он «надстраивается» над
  уже работающим nginx на ISP и пользователями SSH на HQ-CLI.
* Сервер времени поднимается первым же скриптом (на ISP), чтобы все
  остальные узлы могли сразу синхронизироваться при своей настройке.

Каждый скрипт в конце печатает блок **NEXT STEP** — «что запускать дальше и
что подготовить руками перед этим». Это способ зашить приведённый выше
порядок прямо в вывод, чтобы не держать его в голове.

## 4. Сквозные решения, общие для всех скриптов

### 4.1. etcnet — сетевая подсистема ALT Linux

ALT использует не NetworkManager и не `/etc/network/interfaces`, а
собственную систему **etcnet**: каждый интерфейс — это каталог
`/etc/net/ifaces/<имя>/` с набором файлов:

| Файл | Смысл |
|---|---|
| `options` | тип интерфейса и способ настройки (`TYPE=eth/vlan/iptun`, `BOOTPROTO=static/dhcp`, …) |
| `ipv4address` | статический адрес(а) в формате `адрес/маска` |
| `ipv4route` | статические маршруты, например `default via 172.16.1.1` |
| `resolv.conf` | DNS-настройки, которые при поднятии интерфейса вливаются в `/etc/resolv.conf` |

Поэтому скрипты не вызывают `ip addr add` — они **пишут файлы**, а затем
делают `systemctl restart network`. Так настройки переживают перезагрузку:
etcnet при старте прочитает те же файлы и восстановит конфигурацию.

Глобальные параметры ядра etcnet держит в `/etc/net/sysctl.conf` — там же
включается маршрутизация (`net.ipv4.ip_forward`).

### 4.2. Почему DNS переключается «в самом конце» каждого скрипта

Почти в каждом скрипте есть блок:

```bash
# Point DNS at HQ-SRV - done last, everything above still needs
# the public resolver
cat > /etc/net/ifaces/enp7s1/resolv.conf <<EOF
nameserver 192.168.100.2
search tkhis.pro
EOF
cp /etc/net/ifaces/enp7s1/resolv.conf /etc/resolv.conf
```

Итоговая цель — чтобы **все узлы стенда использовали один внутренний DNS**
на HQ-SRV (`192.168.100.2`), который знает имена `*.tkhis.pro`. Но во
время работы скрипта ещё нужно скачивать пакеты, а внутренний DNS может быть
ещё не поднят (например, `hq-rtr.sh` запускается раньше `hq-srv.sh`). Если
переключить DNS в начале, все следующие `apt-get install` упадут на
разрешении имён. Поэтому переключение — последнее действие перед проверками.

Исключение — **HQ-RTR**: `hq-rtr.sh` идёт до `hq-srv.sh`, поэтому в конце
он явно оставляет `nameserver 77.88.8.8`, а на `192.168.100.2` роутер
переключает `hq-rtr-2.sh` — уже после того, как на HQ-SRV поднят dnsmasq.

Почему запись делается **дважды**:

* `/etc/net/ifaces/enp7s1/resolv.conf` — **постоянная** настройка: etcnet
  применит её при следующем рестарте сети или перезагрузке;
* `cp … /etc/resolv.conf` — **немедленное** применение без рестарта сети
  (рестарт мог бы, например, оборвать SSH-сессию, из которой запущен скрипт).

`search tkhis.pro` позволяет обращаться к узлам по короткому имени:
`ping hq-srv` превратится в `hq-srv.tkhis.pro`.

Исключения:

* **ISP** DNS не трогает вовсе — он «провайдер», стоит вне компании и не
  обязан пользоваться её DNS (коммит `7fc548e Leave ISP's resolv.conf alone`);
* **HQ-SRV** указывает на `127.0.0.1` — он сам и есть DNS-сервер;
* **HQ-CLI** DNS получает по DHCP от HQ-RTR, поэтому в его скрипте
  переключения нет.

### 4.3. Временный DNS `77.88.8.8`

В подсказках NEXT STEP и в DHCP на HQ-RTR сначала фигурирует `77.88.8.8` —
это публичный Яндекс.DNS. Он используется как «временные костыли», пока
внутренний DNS не готов: узлу нужно разрешать имена репозиториев и
GitHub, чтобы скачать собственный скрипт. Тот же адрес остаётся upstream-
форвардером у dnsmasq на HQ-SRV — все внешние имена в итоге резолвятся через
него.

### 4.4. Учётные данные

Во всех скриптах используется один пароль `P@ssw0rd` — это **требование
задания**, а не рекомендация. В коде он лежит открытым текстом, потому что
стенд учебный и изолированный; в реальной инфраструктуре так делать нельзя.

| Где | Пользователь | Назначение |
|---|---|---|
| HQ-RTR, BR-RTR | `net_admin` | администратор сетевого оборудования |
| HQ-SRV, BR-SRV, HQ-CLI | `sshuser` (UID 2027) | вход по SSH, Ansible |
| ISP | `root` | ISP — «чужая» машина провайдера, вход по root разрешён, чтобы `gost.sh` мог положить туда сертификаты |
| Samba AD | `Administrator`, `hquser1..5` | доменные учётные записи |

### 4.5. ALT-специфичные команды, которые встречаются везде

* `apt-get` — в ALT это apt поверх **RPM** (не dpkg). Поэтому проверки
  установленных пакетов делаются через `rpm -q`, а не `dpkg -l`.
* `control <фича> <состояние>` — ALT-механизм переключения системных
  политик (например, `control openssl-gost enabled`). Вместо ручной правки
  конфигов он атомарно меняет права/файлы по заранее описанной схеме.
* `gpasswd` в минимальной установке ALT отсутствует — он в пакете
  `shadow-groups`, поэтому маршрутизаторы его доустанавливают.
* SSH-конфиг лежит в `/etc/openssh/sshd_config`, а не в `/etc/ssh/`.
* Группа `wheel` в ALT важнее, чем кажется: по умолчанию `control sudo`
  стоит в режиме `wheelonly`, то есть **сам бинарник `sudo` может запустить
  только член группы wheel**. Запись в `/etc/sudoers` без членства в wheel не
  сработает — поэтому скрипты делают и то и другое.

### 4.6. Синхронизация времени (chrony)

Каждый узел, кроме ISP, получает одинаковый блок:

```bash
apt-get install -y chrony
cat > /etc/chrony.conf <<EOF
server 172.16.1.1 iburst        # в филиале: 172.16.2.1
EOF
systemctl enable --now chronyd
systemctl restart chronyd
chronyc waitsync 15 0 0 2 >/dev/null
```

**Зачем.** Единое время нужно для Kerberos в домене Samba (допуск —
5 минут), для проверки срока действия сертификатов, для сопоставления
логов разных машин. Требование задания — синхронизироваться с ISP.

* **`chrony`**, а не `ntpd`, — современная реализация NTP, стандартная в
  ALT, быстро сходится и хорошо переносит нестабильную сеть ВМ.
* **Сервер — ближайший адрес ISP**: узлы головного офиса обращаются к
  `172.16.1.1`, филиала — к `172.16.2.1`. Трафик до ISP идёт через NAT
  маршрутизатора, поэтому ISP видит запросы с `172.16.x.2` — это учтено в
  его `allow` ([02-isp.md §3](02-isp.md#3-сервер-времени-chrony)).
* **Файл перезаписывается целиком** (`>`) — стандартный конфиг указывает
  на публичные пулы NTP, которые в стенде не нужны.
* **`iburst`** — при старте серия из нескольких запросов вместо одного:
  синхронизация за секунды, а не минуты.
* **`chronyc waitsync 15 0 0 2`** — подождать до 15 попыток с интервалом
  2 с (≈30 с), пока время не синхронизируется (два нуля — не ограничивать
  остаточную коррекцию и перекос). Без этого проверка ниже почти всегда
  давала бы FAIL — скрипт идёт быстрее, чем chrony успевает сойтись.

Проверка `chronyc -n sources | grep "^\^\* 172.16.1.1 "` ищет источник с
маркером `^*` — «выбран и синхронизирован». Одной строки в конфиге для
этого мало: нужно, чтобы сервер реально отвечал.

### 4.7. Часовой пояс

Каждый узел ставит пояс `Asia/Krasnoyarsk` (требование задания). ISP
делает это подробно ([02-isp.md](02-isp.md)), остальные — одним блоком
перед настройкой chrony:

```bash
apt-get install -y tzdata
timedatectl set-timezone Asia/Krasnoyarsk || ln -sf /usr/share/zoneinfo/Asia/Krasnoyarsk /etc/localtime
```

* **`tzdata`** — в JeOS-образах базы часовых поясов может не быть, тогда
  `timedatectl` не знает зону.
* **`|| ln -sf …`** — запасной путь, если `timedatectl` всё равно
  отказался: `/etc/localtime` указывает на файл зоны напрямую.
* Проверка `Local time is UTC+7` смотрит на итог (`date +%z` = `+0700`), а
  не на то, какой командой он получен.

Там же скрипты ставят **`sshpass`** (вход по SSH с паролем без запроса) и включают **`sshd` в автозагрузку**
(`systemctl enable --now sshd`), а не только перезапускают его.

### 4.8. Как VLAN 100/200 доходит до HQ-SRV и HQ-CLI: два сценария

На стенде встречаются два варианта подключения машин головного офиса в
Proxmox. **HQ-RTR в обоих одинаковый**: его карта `enp7s2` без тега на
VLAN-aware мосту, VLAN он разбирает сам подынтерфейсами
`enp7s2.100/.200/.999`. Различаются только HQ-SRV и HQ-CLI:

| | Proxmox тегирует (`proxmox`, по умолчанию) | ВМ тегирует сама (`manual`) |
|---|---|---|
| Карта HQ-SRV в Proxmox | `VLAN Tag = 100` | без тега |
| Карта HQ-CLI в Proxmox | `VLAN Tag = 200` | без тега |
| Адрес HQ-SRV | на `enp7s1` | на `enp7s1.100` (`TYPE=vlan`, `VID=100`) |
| Адрес HQ-CLI (DHCP) | на `enp7s1` | на `enp7s1.200` (`nmcli` или etcnet) |

Смешивать нельзя: тег в Proxmox **плюс** подынтерфейс внутри ВМ — это
двойной тег, и HQ-RTR такую машину не видит.

**Как выбирается сценарий.**

* `hq-rtr.sh` в конце спрашивает: `1` — Proxmox тегирует, `2` — ВМ сама.
  Enter (или запуск без терминала) — `1`. Вопрос можно пропустить:
  `VLAN_MODE=manual ./hq-rtr.sh` или `VLAN_MODE=proxmox …`.
* Баннер печатает команды **только для выбранного** сценария — оба
  целиком в окно не помещаются. Те же команды сохраняются рядом со
  скриптом: `./hq-srv-steps proxmox|manual` печатает любой из вариантов,
  если выбор оказался неверным.
* Ответ записывается в `vlan-mode` рядом со скриптом. `hq-rtr-2.sh` берёт
  его оттуда и печатает подходящие шаги для HQ-CLI (тоже сохраняются:
  `./hq-cli-steps proxmox|manual`). Если файла нет — спрашивает сам.
* `hq-srv.sh` и `hq-cli.sh` ничего не спрашивают, а **определяют сценарий
  сами**: есть `enp7s1.100` / `enp7s1.200` — значит, ВМ тегирует сама.
  От этого зависят интерфейс в проверках и подсказки при обрыве связи.

Подробнее о каркасе, который повторяется в каждом скрипте (переменные,
функция `check`, файлы `retry`/`delete`, самоудаление), — в
[01-script-skeleton.md](01-script-skeleton.md).
