# 07. BR-SRV — `br-srv.sh`, Ansible (`inventory2.yml`, `get_hostname.yml`)

**Роль узла.** Сервер филиала:

* SSH-доступ для `sshuser` (точно так же, как на HQ-SRV);
* **станция управления Ansible** — отсюда автоматизированно управляются
  остальные узлы;
* позже — **контроллер домена Samba AD** (`samba.sh`, см.
  [08-samba.md](08-samba.md));
* ещё позже — **Docker-приложение** `testapp` (`docker.sh`, см.
  [09-web-services.md](09-web-services.md)).

**Сеть.** `enp7s1`, `192.168.0.2/28`, шлюз `192.168.0.1` — задаются руками
по подсказке из `br-rtr.sh`.

**Почему Ansible именно на BR-SRV.** Требование задания. Логически это
тоже оправдано: BR-SRV — сервер, а не рабочая станция, работает постоянно
и через туннель видит все подсети обоих офисов.

---

## 1. SSH и `sshuser`

Идентично HQ-SRV ([05-hq-srv.md §3](05-hq-srv.md#3-ssh-и-пользователь-sshuser)).
Отличие в порядке: здесь сначала проверки SSH, затем Ansible — поэтому
первая порция `check` выполняется посреди скрипта.

Этот сервер доступен снаружи через DNAT на BR-RTR:
`ssh -p 2027 sshuser@172.16.2.2` → попадаете сюда
([04-br-rtr.md §6](04-br-rtr.md#6-nat-и-проброс-портов)).

## 2. Установка Ansible и инвентаря

```bash
apt-get update && apt-get install -y ansible sshpass
mkdir -p /etc/ansible
cd /etc/ansible
wget raw.githubusercontent.com/19zammik86-source/DEMO/refs/heads/main/inventory.yml
```

* **`ansible`** — система управления конфигурацией без агентов: подключается
  к узлам по обычному SSH и выполняет там модули на Python.
* **`sshpass`** — утилита, подставляющая пароль в SSH неинтерактивно.
  Ansible использует её, когда в инвентаре задан `ansible_password` (вход по
  паролю, а не по ключу). Без `sshpass` Ansible откажется работать с
  паролями.
* **`/etc/ansible/`** — каталог Ansible по умолчанию.
* **Инвентарь скачивается из внешнего репозитория** `19zammik86-source/DEMO`,
  а не из этой ветки. Это значит, что содержимое инвентаря этой веткой **не
  контролируется** (см. [11-notes.md](11-notes.md)). Файл
  `inventory2.yml` в этом репозитории — его упрощённый локальный аналог
  (см. §7 ниже).

## 3. `ansible.cfg`

```ini
[defaults]
interpreter_python = /usr/bin/python3
inventory = /etc/ansible/inventory.yml
host_key_checking = false
```

| Параметр | Зачем |
|---|---|
| `interpreter_python` | явно указать Python на управляемых узлах. Без этого Ansible «угадывает» интерпретатор и выдаёт предупреждение на каждый узел; на ALT путь `/usr/bin/python3` стабилен |
| `inventory` | инвентарь по умолчанию — не нужно каждый раз писать `-i …` |
| `host_key_checking = false` | не спрашивать подтверждение неизвестного ключа хоста. При первом подключении к каждому узлу SSH спросил бы `yes/no`, а в неинтерактивном Ansible это означает ошибку. В изолированном стенде риск MITM несущественен |

## 4. Синхронизация времени

chrony-клиент с сервером `172.16.2.1` (ISP со стороны филиала) — см.

## 6. Проверка связности и Ansible (после самоудаления скрипта)

Эта часть идёт **после** `retry`/`delete` и `rm "$SELF"`, в самом конце.
Причина: она интерактивная и может надолго остановиться — служебные файлы
должны быть созданы до этого.

### 6.1. SSH-вход на каждый узел

```bash
sshpass -p 'P@ssw0rd' ssh -p 2027 net_admin@192.168.100.1   # HQ-RTR
sshpass -p 'P@ssw0rd' ssh -p 2027 net_admin@192.168.0.1     # BR-RTR
sshpass -p 'P@ssw0rd' ssh -p 2027 sshuser@192.168.100.2     # HQ-SRV
sshpass -p 'P@ssw0rd' ssh -p 2027 sshuser@192.168.0.2       # BR-SRV (сам себе)
```

**Зачем.** Ручная, наглядная проверка того, что учётные данные и порт на
каждом узле верны, **до** того как запускать Ansible. Каждая команда
открывает интерактивную сессию на узле: убедились, что вход работает, —
`exit`, и скрипт переходит к следующему.

Маршрутизаторы опрашиваются по их **LAN-адресам**: из филиала до
`192.168.100.1` путь идёт через туннель, что одновременно проверяет OSPF.

### 6.2. Поиск HQ-CLI

```bash
for i in $(seq 2 10); do
    IP="${SUBNET}.${i}"
    ping -c 1 -W 1 "$IP" &>/dev/null || continue
    if timeout "$TIMEOUT" bash -c "</dev/tcp/$IP/$PORT" 2>/dev/null; then
        FOUND_IP="$IP"
        break
    fi
done
```

HQ-CLI получает **случайный** адрес из DHCP-пула `.2–.10`, так что заранее
его не знает ни инвентарь, ни DNS. Скрипт перебирает весь пул и ищет адрес,
на котором открыт TCP-порт 2027 (SSH `sshuser`).

* **Сначала `ping` с таймаутом 1 с.** Если адрес никем не занят, попытка
  TCP-подключения к нему висела бы до таймаута; пинг отсекает пустые
  адреса за секунду.
* **`bash -c "</dev/tcp/$IP/$PORT"`** — встроенный в bash псевдофайл: попытка
  открыть его = попытка TCP-соединения. Используется вместо `nc`, которого
  в ALT по умолчанию нет (так же сделано в `gost.sh`).
* **`timeout 3`** — ограничение на само подключение.

Порт 2027 выбран как «подпись» HQ-CLI: в VLAN 200 других узлов с SSH на
этом порту нет.

```bash
sed -i "/^ *hq-cli:/,/ansible_host:/ s/ansible_host: .*/ansible_host: $FOUND_IP/" /etc/ansible/inventory.yml
```

Найденный адрес вписывается в инвентарь. Диапазон `/^ *hq-cli:/,/ansible_host:/`
— «от строки `hq-cli:` до ближайшей `ansible_host:`», и замена делается
только внутри него: у других узлов `ansible_host` не трогается.

### 6.3. `ansible -m ping all`

Модуль `ping` Ansible — это **не ICMP-пинг**: он подключается по SSH,
запускает Python и возвращает `pong`. Успех означает, что узел полностью
готов к управлению (сеть, SSH, пароль, Python). Это финальная сквозная
проверка всего стенда.

### 6.4. Вход на HQ-CLI

Если HQ-CLI найден — интерактивная SSH-сессия на нём, по аналогии с §6.1.

## 7. `inventory2.yml`

```yaml
all:
  hosts:
    hq-srv:
      ansible_host: 192.168.100.2
      ansible_port: 2027
      ansible_password: P@ssw0rd
      ansible_user: sshuser
    hq-cli:
      ansible_host: 192.168.200.2
      ...
```

Инвентарь в YAML-формате: группа `all`, в ней узлы с параметрами
подключения.

| Параметр | Смысл |
|---|---|
| `ansible_host` | адрес для подключения (имя в инвентаре — `hq-srv` — это лишь метка) |
| `ansible_port: 2027` | нестандартный порт SSH |
| `ansible_user` / `ansible_password` | вход по паролю — для этого нужен `sshpass` |

Содержит только `hq-srv` и `hq-cli` — ровно те узлы, на которые нацелен
`get_hostname.yml`. `br-srv.sh` этот файл **не использует** (он качает
внешний `inventory.yml`); `inventory2.yml` можно указать явно:
`ansible-playbook -i inventory2.yml get_hostname.yml`. Адрес HQ-CLI в нём
зафиксирован как `.2` — при другом адресе его надо поправить.

## 8. `get_hostname.yml` — плейбук сбора сведений

```yaml
- name: Get_hostname
  hosts: hq-srv,hq-cli
  gather_facts: true
```

**Зачем.** Требование задания: собрать с узлов их имена и IP-адреса в
файлы на управляющей машине. Демонстрирует использование фактов Ansible.

| Элемент | Смысл |
|---|---|
| `hosts: hq-srv,hq-cli` | целевые узлы — по именам из инвентаря |
| `gather_facts: true` | перед задачами собрать «факты» узла (имя, адреса, ОС…) — из них берутся `ansible_hostname` и `ansible_default_ipv4` |

**Задачи:**

1. **Create info directory** — `file: state=directory` создаёт
   `/etc/ansible/PC_INFO`.
   * `delegate_to: localhost` — выполнить **на управляющей машине**
     (BR-SRV), а не на целевом узле: каталог нужен там, где работает Ansible.
   * `run_once: true` — один раз, а не по разу на каждый узел.
   * `mode: '0755'` — в кавычках, чтобы YAML не прочитал это как
     восьмеричное/десятичное число.
2. **Save hostname and ip** — модуль `copy` с `content:` создаёт файл
   `PC_INFO/<hostname>.yml` с двумя строками. Факты берутся **с целевого
   узла**, а файл пишется **на localhost** (опять `delegate_to`). Имя файла
   от `ansible_hostname` — у каждого узла свой файл.
3. **Verify that the info file was written** — модуль `stat` проверяет файл
   и сохраняет результат в переменную `info_file` (`register`).
4. **Fail if the info file is missing** — `assert` с понятными
   сообщениями на русском. Шаги 3–4 — та же идея, что и функция `check()` в
   bash-скриптах: не верить на слово, а проверить результат.

Каталог называется `PC_INFO` (с подчёркиванием, а не дефисом) — он был
намеренно переименован отдельным коммитом `ac9789d`, и то же имя
используется в сообщениях `assert` (коммит `4ccb9c6`).
