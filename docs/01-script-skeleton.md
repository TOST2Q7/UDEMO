# 01. Каркас скрипта: общие элементы всех `.sh`

Все скрипты ветки построены по одному шаблону. Чтобы не повторять одно и то же
в каждом документе, здесь один раз объясняется каждый общий элемент: зачем он
нужен, как устроен и почему сделан именно так.

Схема любого скрипта:

```
1. Блок переменных (SELF, DIR, NAME, LOG, RAW_URL [+ свои])
2. Собственно настройка узла
3. Переключение DNS (почти везде — последним действием настройки)
4. Функция check() и список проверок → лог *-check.log
5. Создание вспомогательных файлов retry и delete
6. Самоудаление скрипта
7. Баннер NEXT STEP
8. exec bash (не во всех)
```

---

## 1. Блок переменных

```bash
SELF="$(readlink -f "$0")"
DIR="$(dirname "$SELF")"
NAME="$(basename "$SELF")"
LOG="$DIR/${NAME%.sh}-check.log"
RAW_URL="https://raw.githubusercontent.com/TOST2Q7/UDEMO/refs/heads/checks/$NAME"
```

### `SELF="$(readlink -f "$0")"`
`$0` — то, как скрипт был вызван (`./isp.sh`, `bash isp.sh`,
`/root/isp.sh`…). Это может быть относительный путь или символическая ссылка.
`readlink -f` превращает его в **абсолютный канонический путь**.
Зачем: позже скрипт удаляет сам себя и генерирует файл `retry`, в котором
путь зашивается навсегда. Относительный путь в `retry` сломался бы, если
запустить его из другого каталога.

### `DIR="$(dirname "$SELF")"`
Каталог, где лежит скрипт. Все побочные файлы (лог, `retry`, `delete`,
заранее скачанные `gost-*.sh`, УЦ в `gost-ca/`) кладутся **рядом со
скриптом**, а не в текущий каталог. Так всё, что сделал скрипт, собрано в
одном месте и может быть удалено одним `delete`.

### `NAME="$(basename "$SELF")"`
Имя файла скрипта (`isp.sh`). Используется в трёх местах: в имени лога, в
URL для повторного скачивания и в комментарии внутри `delete`.
Благодаря этому **один и тот же каркас копируется между скриптами без
правок** — имя подставляется само.

### `LOG="$DIR/${NAME%.sh}-check.log"`
`${NAME%.sh}` — bash-подстановка «отрезать суффикс `.sh`». Из `isp.sh`
получается `isp-check.log`. В лог попадают только результаты проверок
(`[OK]…` / `[FAIL]…`) без цветовых кодов — чтобы его можно было потом
открыть, показать или сравнить.

### `RAW_URL=".../refs/heads/checks/$NAME"`
Прямая ссылка на «сырой» файл этого же скрипта в ветке `checks` на GitHub.
Используется:
* в `retry` — чтобы скачать свежую версию и перезапустить;
* через `$(dirname "$RAW_URL")` — чтобы получить URL каталога ветки и скачать
  соседние файлы (`dnsmasq.conf`, `gost-isp.sh`, `gost-hqcli.sh`).

Почему именно ветка `checks`, а не `main`: исправления и проверки
разрабатываются в этой ветке, и `retry` должен тянуть **ту же** версию, что
запускалась (коммит `1d6617e Point retry's RAW_URL at the checks branch`).

> В `hq-cli.sh` URL записан как `.../UDEMO/checks/$NAME` (без `refs/heads/`).
> raw.githubusercontent.com понимает обе формы, так что поведение одинаково.

## 2. Функция `check()`

```bash
check() {
    local desc="$1"; shift
    local result
    if eval "$*" &>/dev/null; then
        result="[OK] $desc"
        echo -e "${GREEN}${result}${NC}"
    else
        result="[FAIL] $desc"
        echo -e "${RED}${result}${NC}"
    fi
    echo "$result" >> "$LOG"
}
```

**Зачем.** Скрипты выполняются без `set -e`: одна неудачная команда не
останавливает весь процесс (иначе, например, уже существующий пользователь
при повторном запуске обрывал бы настройку). Обратная сторона — ошибки
легко пропустить в длинном выводе `apt-get`. Функция `check` в конце
**независимо перепроверяет итоговое состояние системы** и выдаёт короткую
сводку зелёным/красным. Смотреть нужно на неё, а не на промежуточный вывод.

**Как устроена.**
* Первый аргумент — человекочитаемое описание, `shift` убирает его.
* Всё остальное (`$*`) — проверочная команда в виде строки. `eval`
  выполняет её как bash-код, поэтому внутри можно использовать `|`, `&&`,
  `!`, `[ … ]` — то, что нельзя передать просто списком аргументов.
* `&>/dev/null` — вывод проверочной команды не нужен, важен только код
  возврата (0 → OK, иначе → FAIL).
* Результат дублируется в лог без цвета.

**Почему проверки пишутся в одинарных кавычках:**

```bash
check "Hostname = isp.au-team.irpo" '[ "$(hostnamectl --static)" = "isp.au-team.irpo" ]'
```

Одинарные кавычки не дают bash подставить `$(…)` в момент вызова `check` —
подстановка произойдёт внутри `eval`, то есть именно в момент проверки. В
`gost*.sh` местами используются двойные кавычки — там это сделано нарочно,
чтобы переменные вроде `$CA_KEY` подставились заранее, а внутренние кавычки
экранированы `\"`.

**Почему проверяется «реальное состояние», а не конфиг, когда это возможно.**
Например, `ip -4 addr show enp7s2 | grep 172.16.1.1/28` проверяет, что адрес
**действительно висит на интерфейсе**, а не просто записан в файл. Там, где
реальное состояние проверить трудно (sshd_config, sudoers), проверяется
содержимое конфига.

**Цвета.** `GREEN`, `RED`, `CYAN`, `YELLOW`, `NC` — ANSI escape-коды. `NC`
(No Color) сбрасывает цвет. `echo -e` нужен, чтобы `\033` интерпретировался
как ESC.

### `: > "$LOG"`
`:` — пустая команда bash, `>` — перенаправление с перезаписью. Вместе —
идиома «обнулить файл». Лог очищается перед каждой серией проверок, чтобы при
повторном запуске не смешивались старые и новые результаты.

### `echo "=== … ===" | tee -a "$LOG"`
`tee -a` одновременно выводит строку на экран и дописывает в лог — заголовок
и футер нужны и там и там.

### Важно: `[FAIL]` не всегда означает ошибку в этом скрипте
Некоторые проверки зависят от **других** узлов. Например, `hq-rtr.sh`
проверяет пинг до `192.168.100.2` (HQ-SRV) и до `10.10.10.2` (BR-RTR), хотя
по порядку запуска эти узлы ещё не настроены. Такие FAIL ожидаемы при первом
прогоне и исчезают, если перезапустить скрипт (`./retry`) позже.

## 3. Файл `retry`

```bash
cat > "$DIR/retry" <<RETRYEOF
#!/bin/bash
wget -O "$SELF" "$RAW_URL"
chmod +x "$SELF"
exec "$SELF"
RETRYEOF
chmod +x "$DIR/retry"
```

**Зачем.** Скрипт удаляет себя после выполнения (см. ниже). Если что-то
пошло не так или в репозиторий залили исправление, нужен способ одной
командой получить **свежую версию из GitHub и выполнить её снова**. Это и
есть `./retry`.

**Почему heredoc без кавычек (`<<RETRYEOF`, а не `<<'RETRYEOF'`).** Без
кавычек bash подставляет переменные **в момент создания файла**. В
результате в `retry` попадают уже готовые абсолютные пути и URL, например:

```bash
#!/bin/bash
wget -O "/root/isp.sh" "https://raw.githubusercontent.com/.../checks/isp.sh"
chmod +x "/root/isp.sh"
exec "/root/isp.sh"
```

Файл получается самодостаточным и не зависит от переменных окружения.

**Почему `exec`.** `exec` заменяет процесс `retry` процессом скрипта, не
оставляя лишний уровень вложенности shell-ов.

## 4. Файл `delete`

```bash
cat > "$DIR/delete" <<DELEOF
#!/bin/bash
# Removes everything created by $NAME in this directory
rm -f "$LOG" "$DIR/retry" "$DIR/delete" "$SELF"
DELEOF
```

**Зачем.** Убрать за собой все служебные файлы: лог, `retry`, сам `delete`
и (если он был перекачан через `retry`) скрипт. Список файлов свой у каждого
скрипта — например, `isp.sh` дополнительно удаляет заранее скачанные
`gost-isp.sh` и `proxy.sh`, `hq-srv.sh` — скачанный `dnsmasq.conf`, а `gost.sh` —
целиком каталог УЦ `gost-ca/` (поэтому там `rm -rf`).

**Важно:** `delete` удаляет только **файлы в каталоге скрипта**. Настройки
системы (адреса, пользователи, сервисы) он не откатывает — это не
«деинсталлятор».

**Удаление самого себя.** `rm` удаляет `delete` во время его выполнения —
в Linux это безопасно: bash уже держит файл открытым и дочитает его.

## 5. Самоудаление: `rm -f "$SELF"`

После проверок скрипт удаляет собственный файл. Причины:

* **Повторный случайный запуск опасен**: многие команды не идемпотентны
  (`>> /etc/sudoers`, `>> /etc/fstab`, `iptables -A`, `mdadm --create`) —
  второй прогон создаст дубликаты. Отсутствие файла — защита «от пальца».
* **Каталог остаётся чистым**: после работы видны только `retry`,
  `delete` и лог, по которым понятно, что скрипт уже отрабатывал.
* Если нужно всё же перезапустить — для этого есть осознанное действие
  `./retry`.

## 6. Баннер NEXT STEP

В конце каждого скрипта — рамка с текстом «что запускать дальше, на каком
узле, в каком сегменте и что предварительно сделать руками». Это
«встроенная навигация» по порядку развёртывания, описанному в
[00-overview.md](00-overview.md#3-порядок-запуска-и-почему-он-такой).

Почему часть действий предлагается **сделать руками**, а не скриптом: скрипт
следующего узла ещё нужно **скачать**, а для этого узлу уже нужны адрес,
шлюз и DNS. Курица и яйцо: минимальную сетевую связность приходится задать
вручную, остальное скрипт сделает сам. Поэтому баннер печатает готовые
команды `echo … > /etc/net/ifaces/…` для следующего узла.

## 7. `exec bash` в конце

Большинство скриптов заканчиваются `exec bash`.

**Зачем.** Скрипт меняет имя узла через `hostnamectl`, но приглашение
командной строки текущего shell-а продолжает показывать старое имя — оно
вычисляется при старте shell-а. `exec bash` заменяет процесс скрипта новым
интерактивным bash-ем, который заново читает имя хоста, профиль и
переменные — пользователь сразу видит `root@hq-rtr` вместо
`root@localhost`. Также это удобно, если скрипт запущен через конвейер
(`wget -O- … | bash`): вместо выхода остаётся рабочий терминал.

В скриптах `hq-rtr-2.sh`, `hq-cli.sh`, `samba.sh`, `gost.sh`, `gost-isp.sh`,
`gost-hqcli.sh` `exec bash` нет: они либо не меняют имя хоста, либо
(`hq-cli.sh`) это просто не было добавлено — после них достаточно заново
войти в систему, чтобы увидеть новое имя в приглашении.

## 8. Заранее скачиваемые файлы (pre-fetch)

`isp.sh` скачивает `proxy.sh` и `gost-isp.sh`, а `hq-cli.sh` —
`gost-hqcli.sh`, но **не запускают** их:

```bash
wget -O "$DIR/gost-isp.sh" "$(dirname "$RAW_URL")/gost-isp.sh" && chmod +x "$DIR/gost-isp.sh" \
    || echo "Could not pre-fetch gost-isp.sh, fetch it manually later" >&2
```

Причина: эти этапы выполняются в самом конце, когда на этих узлах DNS уже
может быть переключён на внутренний, а доступ в интернет — ограничен
условиями стенда. Скачать скрипт заранее, пока интернет точно работает,
надёжнее. Конструкция `A && B || C` печатает предупреждение, если скачать
не удалось, но не прерывает основную настройку.
