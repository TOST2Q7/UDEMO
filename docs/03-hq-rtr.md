# 03. HQ-RTR — `hq-rtr.sh` и `hq-rtr-2.sh`

**Роль узла.** Маршрутизатор головного офиса. Самый «насыщенный» узел
стенда: он одновременно

* терминирует три VLAN офиса (серверы, клиенты, управление);
* раздаёт адреса клиентам по DHCP;
* держит GRE-туннель в филиал и обменивается с ним маршрутами по OSPF;
* выпускает офис в интернет через NAT и пробрасывает порт сайта на HQ-SRV;
* синхронизирует время с ISP;
* принимает администраторов по SSH на нестандартном порту.

**Интерфейсы.**

| Интерфейс | Назначение | Адрес |
|---|---|---|
| `enp7s1` | WAN, к ISP | `172.16.1.2/28` (задаётся руками до скрипта) |
| `enp7s2` | trunk в сторону офиса, без адреса | — |
| `enp7s2.100` | VLAN 100 — серверы | `192.168.100.1/27` |
| `enp7s2.200` | VLAN 200 — клиенты | `192.168.200.1/28` |
| `enp7s2.999` | VLAN 999 — управление | `192.168.99.1/29` |
| `tun0` | GRE-туннель в BR-RTR | `10.10.10.1/24` |

---

## Часть 1. `hq-rtr.sh`

### 1.1. Имя хоста и `shadow-groups`

```bash
hostnamectl set-hostname hq-rtr.tkhis.pro
apt-get install shadow-groups -y
```

`shadow-groups` содержит утилиту `gpasswd`, которая понадобится ниже для
добавления `net_admin` в группу `wheel`. В минимальном образе ALT её нет.
Ставится в самом начале — пока DNS ещё публичный и репозиторий доступен.

### 1.2. Trunk-интерфейс `enp7s2`

```bash
mkdir -p /etc/net/ifaces/enp7s2
cp -r /etc/net/ifaces/enp7s1/options /etc/net/ifaces/enp7s2/options
```

Физический порт `enp7s2` — **транк**: по нему идут кадры всех трёх VLAN с
тегами 802.1Q. Сам он адреса не имеет (файла `ipv4address` нет) — адреса
висят на VLAN-подынтерфейсах. Но etcnet должен знать о нём и поднимать его,
иначе не поднимутся и VLAN поверх.

**Почему `options` копируется с `enp7s1`**, а не пишется с нуля: это быстрый
способ получить валидный для данной системы шаблон Ethernet-интерфейса
(`TYPE=eth` и т. д.) без риска опечатки. Нюанс — `enp7s2` унаследует и
`BOOTPROTO` от `enp7s1` (см. [11-notes.md](11-notes.md)).

### 1.3. VLAN 100, 200, 999

```bash
mkdir -p /etc/net/ifaces/enp7s2.100/
cat > /etc/net/ifaces/enp7s2.100/options <<EOF
TYPE=vlan
HOST=enp7s2
VID=100
BOOTPROTO=static
EOF
echo "192.168.100.1/27" > /etc/net/ifaces/enp7s2.100/ipv4address
```

| Ключ | Зачем |
|---|---|
| `TYPE=vlan` | etcnet создаст 802.1Q-подынтерфейс |
| `HOST=enp7s2` | родительский физический интерфейс; etcnet поднимет его первым |
| `VID=100` | номер VLAN = тег в кадре; должен совпадать с тегом на стороне сервера/коммутатора |
| `BOOTPROTO=static` | адрес из `ipv4address` |

Имя каталога `enp7s2.100` — общепринятая форма «родитель.VID», по ней
сразу видно, что это за интерфейс.

**Смысл трёх VLAN:**

* **100 — серверы** (`/27`, до 30 узлов). Здесь живёт HQ-SRV. Шлюз
  `192.168.100.1`.
* **200 — клиенты** (`/28`, до 14 узлов). Рабочие станции; адреса
  раздаются по DHCP, поэтому это единственная VLAN, где работает dnsmasq.
* **999 — управление** (`/29`, до 6 узлов). Отдельная сеть для
  административного доступа к оборудованию — требование задания; в стенде
  узлов в ней нет, но интерфейс и маршрут существуют и анонсируются по OSPF.

### 1.4. Маршрутизация и рестарт сети

```bash
sed -i 's/^#* *net\.ipv4\.ip_forward *=.*/net.ipv4.ip_forward = 1/' /etc/net/sysctl.conf
grep -q "^net.ipv4.ip_forward = 1" /etc/net/sysctl.conf || echo "net.ipv4.ip_forward = 1" >> /etc/net/sysctl.conf
sysctl -w net.ipv4.ip_forward=1
systemctl restart network
```

Как и на ISP, без forwarding маршрутизатор не будет пересылать пакеты между
VLAN, туннелем и WAN — у HQ-SRV и HQ-CLI не будет интернета, хотя шлюз
`.1` пингуется. `sed` ловит строку в любом написании (с пробелами или без,
закомментированную), `grep … || echo` дописывает её, если строки нет вовсе,
а `sysctl -w` включает пересылку сразу, не дожидаясь рестарта сети. Рестарт сети здесь — чтобы **VLAN-интерфейсы
появились до установки dnsmasq**: dnsmasq в конфиге привязывается к
`enp7s2.200`, и интерфейс должен существовать к его старту.

### 1.5. DHCP-сервер (dnsmasq)

```bash
apt-get update && apt-get install -y dnsmasq
cat > /etc/dnsmasq.conf <<EOF
no-resolv
domain=tkhis.pro
dhcp-range=192.168.200.2,192.168.200.10,999h
dhcp-option=3,192.168.200.1
dhcp-option=6,77.88.8.8
dhcp-option=15,tkhis.pro
interface=enp7s2.200
EOF
systemctl enable --now dnsmasq
systemctl restart dnsmasq
```

**Почему dnsmasq, а не ISC dhcpd/Kea.** dnsmasq — лёгкий, конфиг в
несколько строк, стоит в репозитории ALT. Для одной подсети с десятком
клиентов большего не нужно. (Тот же dnsmasq на HQ-SRV работает как
DNS-сервер — один инструмент для двух задач.)

Построчно:

| Строка | Смысл | Почему так |
|---|---|---|
| `no-resolv` | не читать `/etc/resolv.conf` для поиска upstream-DNS | роутер не должен работать DNS-сервером для клиентов; клиентам сразу отдаётся адрес «настоящего» DNS |
| `domain=tkhis.pro` | домен для DHCP-клиентов | клиенты регистрируются как `имя.tkhis.pro` |
| `dhcp-range=…2,…10,999h` | пул `.2`–`.10`, аренда 999 часов | `.1` занят шлюзом; 9 адресов с запасом для стенда; очень длинная аренда (~41 день), чтобы адрес HQ-CLI **не менялся** во время работы — на него опираются Ansible и `gost.sh` |
| `dhcp-option=3,192.168.200.1` | опция 3 — шлюз по умолчанию | адрес этого же роутера во VLAN 200 |
| `dhcp-option=6,77.88.8.8` | опция 6 — DNS-сервер | **временно** публичный: внутреннего DNS ещё нет. Меняется на `192.168.100.2` скриптом `hq-rtr-2.sh` |
| `dhcp-option=15,tkhis.pro` | опция 15 — DNS-суффикс | клиент сможет писать `hq-srv` вместо FQDN |
| `interface=enp7s2.200` | обслуживать только VLAN 200 | DHCP не должен «утечь» во VLAN 100/999 или, что хуже, в WAN к провайдеру |

`enable --now` + `restart`: первое включает автозапуск и стартует, если
сервис стоял; второе гарантирует перечитывание только что записанного
конфига, если сервис уже работал (например, при повторном запуске).

### 1.6. GRE-туннель `tun0`

```bash
cat > /etc/net/ifaces/tun0/options <<EOF
TYPE=iptun
TUNTYPE=gre
TUNLOCAL=172.16.1.2
TUNREMOTE=172.16.2.2
TUNTTL=64
TUNOPTIONS='ttl 64'
HOST=enp7s1
EOF
echo "10.10.10.1/24" > /etc/net/ifaces/tun0/ipv4address
modprobe ip_gre
systemctl restart network
```

**Зачем туннель.** Сети офисов (`192.168.x.x`) — частные, ISP о них не знает
и маршрутизировать их не будет. GRE упаковывает пакет «офис → офис» внутрь
пакета «`172.16.1.2` → `172.16.2.2`», который ISP доставить умеет. Для
обоих маршрутизаторов это выглядит как прямой кабель между ними.

**Почему GRE, а не IPIP/WireGuard/IPsec.** GRE умеет переносить
multicast — а OSPF рассылает свои Hello именно на multicast-адрес
`224.0.0.5`. Через простой IPIP OSPF-соседство бы не установилось.
Шифрования GRE не даёт; в рамках задания это допустимо.

| Ключ | Смысл |
|---|---|
| `TYPE=iptun` | etcnet-тип «IP-туннель» |
| `TUNTYPE=gre` | конкретный протокол инкапсуляции |
| `TUNLOCAL=172.16.1.2` | внешний адрес этого конца (свой WAN) |
| `TUNREMOTE=172.16.2.2` | внешний адрес другого конца (WAN BR-RTR) |
| `TUNTTL=64` / `TUNOPTIONS='ttl 64'` | TTL внешнего пакета. У GRE по умолчанию TTL «наследуется» от внутреннего пакета, а у multicast-пакетов OSPF он равен 1 — внешний пакет умер бы на первом же хопе (ISP). Явный `ttl 64` это исключает. Параметр задан двумя способами для совместимости с разными версиями etcnet |
| `HOST=enp7s1` | туннель зависит от WAN-интерфейса: etcnet поднимет его после `enp7s1` |

Адрес `10.10.10.1/24` — внутренний адрес туннеля, по нему OSPF-соседи видят
друг друга.

`modprobe ip_gre` — загрузить модуль ядра GRE-туннелей прямо сейчас, чтобы
рестарт сети гарантированно смог создать интерфейс. Именно `ip_gre`: модуль
`gre` — лишь общий разборщик GRE-пакетов, сами туннельные интерфейсы
создаёт `ip_gre` (он подтягивает `gre` как зависимость).

### 1.7. FRR и OSPF

```bash
apt-get install frr -y
sed -i 's/ospfd=no/ospfd=yes/' /etc/frr/daemons
systemctl daemon-reload
systemctl enable --now frr
```

**FRR** (Free Range Routing) — пакет демонов динамической маршрутизации.
Каждый протокол — отдельный демон, а файл `/etc/frr/daemons` решает, какие
из них запускать. По умолчанию всё выключено, поэтому `ospfd=no → yes`.

`daemon-reload` — на случай, если установка пакета добавила/изменила
systemd-юниты.

```bash
vtysh << 'EOF'
conf
router ospf
network 192.168.100.0/27 area 0
network 192.168.200.0/28 area 0
network 192.168.99.0/29 area 0
network 10.10.10.0/24 area 0
exit
int tun0
ip ospf authentication message-digest
ip ospf message-digest-key 1 md5 P@ssw0rd
ip ospf network broadcast
no ip ospf passive
do wr
exit
EOF
```

`vtysh` — единая консоль FRR в стиле Cisco IOS. Команды подаются через
heredoc, как если бы их набирали руками. `'EOF'` в кавычках — чтобы bash не
пытался интерпретировать `$`/`@` внутри (важно для пароля).

| Команда | Смысл |
|---|---|
| `conf` | войти в режим конфигурирования |
| `router ospf` | создать/войти в процесс OSPF |
| `network X area 0` | включить OSPF на интерфейсах из этой сети **и** анонсировать саму сеть. Перечислены все три VLAN (чтобы филиал знал, как до них дойти) и сеть туннеля (чтобы по ней установилось соседство) |
| `area 0` | backbone-область. На стенде из двух маршрутизаторов больше одной области не нужно |
| `int tun0` | настройки конкретного интерфейса |
| `ip ospf authentication message-digest` | требовать MD5-аутентификацию OSPF-пакетов на туннеле |
| `ip ospf message-digest-key 1 md5 P@ssw0rd` | ключ №1 и пароль. На BR-RTR должен быть **идентичен**, иначе соседство не поднимется |
| `ip ospf network broadcast` | тип сети OSPF на туннеле — broadcast, как и на BR-RTR (типы на концах должны совпадать). Соседство поднимается после выборов DR, примерно через 40 с |
| `no ip ospf passive` | явно разрешить Hello на `tun0`: через этот интерфейс и устанавливается соседство с филиалом |
| `do wr` | `write memory` — сохранить текущую конфигурацию в `/etc/frr/frr.conf`, иначе она пропадёт при рестарте FRR |

**Почему аутентификация только на `tun0`.** Туннель идёт через «чужую»
сеть провайдера — именно там теоретически может появиться посторонний
OSPF-сосед, способный подсунуть ложные маршруты. Защита нужна на этом
участке (требование задания).

Сеть WAN (`172.16.1.0/28`) в OSPF **не** включена: иначе маршрутизатор
пытался бы искать соседей в сторону ISP, и маршруты до внешних адресов
туннеля могли бы начать ходить через сам туннель (рекурсивная
маршрутизация, туннель «падает»).

### 1.8. NAT

```bash
iptables -t nat -A POSTROUTING -o enp7s1 -j MASQUERADE
iptables -t nat -A PREROUTING -i enp7s1 -p tcp --dport 8080 -j DNAT --to-destination 192.168.100.2:80
iptables -t nat -A PREROUTING -i enp7s1 -p tcp --dport 2027 -j DNAT --to-destination 192.168.100.2:2027
iptables-save > /etc/sysconfig/iptables
systemctl enable --now iptables
```

Офисные `192.168.x.x` маскируются под `172.16.1.2` при выходе к ISP. Логика
та же, что на ISP ([02-isp.md](02-isp.md#6-nat)). В итоге интернет-трафик
офиса проходит **двойной NAT** (HQ-RTR, затем ISP) — нормальная для такого
стенда картина.

Трафик туннеля между офисами под NAT не попадает: он уходит в `tun0`, а
не в `enp7s1` (внешний GRE-пакет в `enp7s1` уходит, но его адрес
источника и так `172.16.1.2`, маскировка ничего не меняет).

**Проброс `8080 → 192.168.100.2:80`.** Сайт на HQ-SRV (`web.sh`) должен
быть доступен обратному прокси на ISP, но ISP не видит частную сеть офиса.
Правило перенаправляет соединения, **пришедшие с WAN** (`-i enp7s1`) на
порт 8080 роутера, на порт 80 HQ-SRV. Смена порта (8080 → 80) позволяет не
трогать Apache: снаружи используется одинаковый порт 8080 для обоих
офисов, внутри — штатный порт сервиса. Как устроены `PREROUTING`/`DNAT` и
почему важен `-i enp7s1` — в [04-br-rtr.md §6](04-br-rtr.md#6-nat-и-проброс-портов);
общая схема веб-сервисов — в [09-web-services.md](09-web-services.md).

**Проброс SSH `2027 → 192.168.100.2:2027`.** Раньше эта строка была
закомментирована: в варианте с `-d <LAN-адрес роутера>` правило
перехватывало SSH к самому роутеру. Сейчас оно, как на BR-RTR, привязано к
входному WAN-интерфейсу (`-i enp7s1`): снаружи порт 2027 ведёт на HQ-SRV,
а изнутри и через туннель — на сам HQ-RTR (см.
[04-br-rtr.md](04-br-rtr.md#6-nat-и-проброс-портов)).

### 1.9. Пользователь `net_admin`

```bash
useradd -m net_admin
echo "net_admin:P@ssw0rd" | chpasswd
gpasswd -a net_admin wheel
echo "net_admin ALL=(ALL) NOPASSWD: ALL" >> /etc/sudoers
```

Требование задания: у сетевого оборудования должен быть отдельный
администратор с полными правами без пароля на sudo.

* `useradd -m` — с домашним каталогом (`-m`), иначе вход по SSH даст
  предупреждения и не будет места для `~/.ssh`.
* `chpasswd` читает `user:password` со stdin — **неинтерактивная** смена
  пароля (в отличие от `passwd`, который спрашивает дважды).
* `gpasswd -a … wheel` — в ALT `sudo` может запустить только член `wheel`
  (см. [00-overview.md](00-overview.md#45-alt-специфичные-команды-которые-встречаются-везде)).
* `NOPASSWD: ALL` — любые команды от любого пользователя без запроса
  пароля. Нужен, в частности, для Ansible (`become`) без ввода пароля.

### 1.10. SSH

```bash
sed -i 's/#Port 22/Port 2027/' /etc/openssh/sshd_config
sed -i 's/#PermitRootLogin without-password/PermitRootLogin no/' /etc/openssh/sshd_config
systemctl restart sshd
```

* **Порт 2027** — требование задания. Практический смысл нестандартного
  порта — отсечь массовых ботов, сканирующих 22-й.
* **`PermitRootLogin no`** — вход только под именным пользователем
  (`net_admin`), а повышение прав — через sudo. Так в логах видно, кто что
  делал.

`sed` заменяет **закомментированные значения по умолчанию** из
стандартного конфига ALT: раскомментирует строку и сразу меняет значение.

### 1.12. DNS пока остаётся публичным

`resolv.conf` → `nameserver 77.88.8.8`. Внутреннего DNS на HQ-SRV ещё нет
(`hq-srv.sh` запускается после этого скрипта), поэтому роутер пока ходит в
публичный резолвер. На `192.168.100.2` + `search tkhis.pro` его
переключает `hq-rtr-2.sh` — вместе с DHCP-опцией для клиентов. Почему запись
делается дважды — в
[00-overview.md](00-overview.md#42-почему-dns-переключается-в-самом-конце-каждого-скрипта).

### 1.13. Проверки

Помимо стандартных (имя, адреса, сервисы, пользователь, SSH, DNS),
интересны эти:

* `dnsmasq listens on VLAN200` — `grep -q "^interface=enp7s2.200$"`: якоря
  `^…$` гарантируют, что это ровно та строка, а не, скажем,
  `interface=enp7s2.2000`.
* `Interface tun0 (GRE) is up` — у интерфейса есть флаг `UP`, а не просто
  он существует.
* `tun0 is GRE 172.16.1.2 -> 172.16.2.2` — `ip -d link` показывает, что это именно GRE
  с правильными внешними адресами: перепутанные `TUNLOCAL`/`TUNREMOTE`
  дали бы интерфейс, который «есть», но никуда не ведёт.
* `Tunnel to branch responds (10.10.10.2)` — пинг другого конца туннеля.
  Будет FAIL, если BR-RTR ещё не настроен, — не ошибка этого скрипта.
* `OSPF neighbour 10.10.10.2 is Full on tun0` — соседство с BR-RTR
  полностью установлено: туннель пропускает multicast, MD5-ключи и тип сети
  совпадают. Если туннель уже отвечает, скрипт перед проверками до ~60 с
  ждёт состояния Full (выборы DR на broadcast-сети занимают ~40 с).
* `HQ-SRV reachable (192.168.100.2)` — при первом прогоне почти всегда FAIL:
  у HQ-SRV ещё нет VLAN 100. Проверка полезна при повторном `./retry`.
* `IP forwarding active now` — `/proc/sys/net/ipv4/ip_forward` равен `1`
  прямо сейчас, а не только в `sysctl.conf`.
* `Internet via NAT from VLAN100 (src .100.1)` — `ping -I 192.168.100.1
  77.88.8.8`: пакет с адресом из VLAN 100 уходит через MASQUERADE. Если
  OK, роутер готов выпустить HQ-SRV в интернет; FAIL — смотреть
  `iptables -t nat -S` и маршрут по умолчанию.
* `Site DNAT (8080 -> HQ-SRV:80) configured` — правило проброса на месте.
* `Time synced from ISP` — источник `172.16.1.1` выбран chrony (`^*`).

### 1.14. NEXT STEP

Баннер даёт команды для HQ-SRV, и они зависят от того, как VLAN 100
доходит до сервера ([00-overview.md §4.8](00-overview.md#48-как-vlan-100200-доходит-до-hq-srv-и-hq-cli-два-сценария)).
Сам HQ-RTR в обоих сценариях настроен одинаково: `enp7s2` без тега, VLAN
разбирают подынтерфейсы `enp7s2.100/.200/.999`.

Перед баннером скрипт спрашивает сценарий (`1` / `2`, Enter = `1`); с
`VLAN_MODE=proxmox|manual` вопроса нет. Печатается вариант только для
выбранного сценария, а оба сохраняются в `./hq-srv-steps`.

**1. Proxmox тегирует (`proxmox`).** У карты HQ-SRV `VLAN Tag = 100`
(у HQ-CLI — `200`), bridge VLAN aware. Внутри HQ-SRV кадры уже без тега,
адрес `192.168.100.2/27`, шлюз `.1` и временный DNS `77.88.8.8` ставятся
прямо на `enp7s1`:

* `rm -rf /etc/net/ifaces/enp7s1.100` — если подынтерфейс остался. Tag=100
  в Proxmox плюс `enp7s1.100` = **двойной тег**, и HQ-RTR не видит сервер;
* `sed … BOOTPROTO=static` — если установщик оставил `dhcp`, etcnet
  проигнорировал бы `ipv4address`.

**2. ВМ тегирует сама (`manual`).** У карт HQ-SRV и HQ-CLI тега нет,
внутри HQ-SRV создаётся `enp7s1.100`:

* `printf '%s\n' TYPE=vlan HOST=enp7s1 VID=100 BOOTPROTO=static > …/enp7s1.100/options`
  — VLAN-подынтерфейс поверх `enp7s1`;
* `enp7s1` остаётся `BOOTPROTO=static` **без адреса** (старые
  `ipv4address`/`ipv4route` удаляются): иначе на нём остался бы второй
  адрес или маршрут по умолчанию мимо VLAN;
* адрес, шлюз и временный DNS — в `enp7s1.100`.

Последняя строка баннера — `./hq-srv-steps <другой сценарий>`: если
выбрали не то, другой вариант печатается без перезапуска скрипта. Ответ
сохраняется в `vlan-mode` для `hq-rtr-2.sh`.

## Часть 2. `hq-rtr-2.sh`

Маленький скрипт, запускаемый на HQ-RTR **второй раз**, после `hq-srv.sh`.

### Зачем отдельный скрипт

На момент `hq-rtr.sh` внутреннего DNS ещё нет, поэтому DHCP раздаёт
клиентам `77.88.8.8`. Когда HQ-SRV поднят, клиенты должны получать его
адрес — иначе они не смогут разрешать `*.tkhis.pro`. Встроить это в
`hq-rtr.sh` нельзя: там HQ-SRV ещё не существует. Отдельный скрипт делает
ровно одно изменение и ничего больше не трогает.

### Что делает

```bash
sed -i 's/^dhcp-option=6,77\.88\.8\.8$/dhcp-option=6,192.168.100.2/' /etc/dnsmasq.conf
systemctl restart dnsmasq
```

* Шаблон с `^…$` и экранированными точками (`77\.88\.8\.8`) — меняется
  **только** эта строка целиком; неэкранированная точка в regex означала бы
  «любой символ».
* `restart dnsmasq` — dnsmasq читает конфиг только при старте.

Затем тот же блок переключения DNS самого роутера, что и в `hq-rtr.sh`.
Повтор безвреден (файл перезаписывается тем же содержимым) и гарантирует
правильный итог, даже если `hq-rtr.sh` запускали в более старой версии,
где этого блока не было.

### Проверки

* новое значение `dhcp-option=6,192.168.100.2` присутствует;
* **старое значение отсутствует** (`! grep …`) — защита от ситуации, когда
  строка продублирована и `sed` поменял только одну;
* dnsmasq работает.

### NEXT STEP

Указывает на `hq-cli.sh`, сценарий берёт из `vlan-mode`, который оставил
`hq-rtr.sh` (`VLAN_MODE=…` перекрывает, без файла скрипт спрашивает сам).
Шаги сохраняются в `./hq-cli-steps proxmox|manual`.

* **Proxmox тегирует.** У карты HQ-CLI `VLAN Tag = 200`, ручной настройки
  сети не нужно — всё придёт по DHCP на `enp7s1`. Если клиент уже получил
  аренду со старым DNS, её нужно обновить (`systemctl restart network` на
  клиенте) — иначе он ещё 999 часов жил бы со старым DNS.
* **ВМ тегирует сама.** У карты HQ-CLI тега нет, внутри создаётся
  `enp7s1.200` с DHCP. HQ-CLI — рабочая станция, сетью там обычно
  управляет NetworkManager, поэтому основной вариант —
  `nmcli con add type vlan … dev enp7s1 id 200 ipv4.method auto`; для
  etcnet баннер даёт и его вариант (`TYPE=vlan`, `VID=200`,
  `BOOTPROTO=dhcp`).
