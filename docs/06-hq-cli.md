# 06. HQ-CLI — `hq-cli.sh`

**Роль узла.** Рабочая станция сотрудника головного офиса (VLAN 200). На
ней проверяется, что всё построенное «работает для пользователя»:
браузер открывает внутренние сайты, сетевой диск подключён, администратор
может зайти удалённо.

**Сеть.** Адрес из пула `192.168.200.2–.6`, шлюз `192.168.200.1`, DNS и
домен приходят по DHCP от HQ-RTR. Именно поэтому в скрипте **нет** блока
переключения DNS. Куда приходит аренда, зависит от сценария
([00-overview.md §4.8](00-overview.md#48-как-vlan-100200-доходит-до-hq-srv-и-hq-cli-два-сценария)):
если Proxmox тегирует VLAN 200 (`VLAN Tag = 200` у карты), то на `enp7s1`
и вручную ничего делать не надо; если ВМ тегирует сама — на `enp7s1.200`,
который создаётся до запуска скрипта по подсказке `hq-rtr-2.sh`.

Скрипт определяет сценарий сам (есть интерфейс `enp7s1.200` — значит,
второй) и проверяет `VLAN 200 address from DHCP on <интерфейс>` и
`Default route via HQ-RTR (192.168.200.1)`.

## 1. Яндекс Браузер

```bash
apt-get update
# Yandex Browser is not installed for now; uncomment to bring it back
# apt-get install -y yandex-browser-stable
```

**Сейчас установка закомментирована**, как и проверка
`Yandex Browser installed`: `apt-get update` остаётся, он нужен остальным
установкам скрипта. Чтобы вернуть браузер, раскомментируйте обе строки в
`hq-cli.sh`.

Ставится первым — это самая «тяжёлая» загрузка, и её лучше сделать, пока
всё остальное ещё не трогали.

**Почему именно Яндекс Браузер.** На финальном этапе
([10-gost.md](10-gost.md)) сайты `web` и `docker` отдаются по HTTPS с
сертификатами на российских алгоритмах ГОСТ Р 34.10-2012 / 34.11-2012.
Обычные сборки Firefox/Chromium такие алгоритмы в TLS не поддерживают;
Яндекс Браузер — из немногих, где поддержка ГОСТ-TLS предусмотрена
(в общем случае ей нужен установленный криптопровайдер). В самом скрипте
причина выбора не записана — это наиболее вероятное объяснение, а также
возможное прямое требование задания.

## 2. Синхронизация времени

chrony-клиент с сервером `172.16.1.1` (ISP) — см.
[00-overview.md §4.6](00-overview.md#46-синхронизация-времени-chrony).
Для клиента это важно прежде всего из-за сертификатов: браузер
сверяет текущее время со сроком действия сертификата, и при «убежавших»
часах даже доверенный ГОСТ-сертификат был бы отвергнут.

## 4. Подключение NFS

```bash
apt-get install -y nfs-clients
mkdir -p /mnt/nfs
sed -i '\#[[:space:]]/mnt/nfs[[:space:]]#d' /etc/fstab
cat >> /etc/fstab <<EOF
192.168.100.2:/raid5/nfs /mnt/nfs nfs rw,_netdev 0 0
EOF
mount -a
ls /mnt/nfs
```

* `nfs-clients` — пакет ALT с `mount.nfs`; без него `mount -t nfs` не
  работает (на Workstation он бывает не установлен).
* `_netdev` — systemd монтирует ресурс только после поднятия сети, иначе
  при загрузке монтирование могло бы сорваться.
* `sed … /mnt/nfs …d` — старая строка для `/mnt/nfs` удаляется, так что
  повторный запуск не дублирует запись в fstab.

* Источник — `192.168.100.2:/raid5/nfs`, экспорт с HQ-SRV
  ([05-hq-srv.md §5](05-hq-srv.md#5-nfs)). Указан **IP-адрес, а не имя**:
  монтирование из fstab происходит при загрузке, и если DNS в этот момент
  недоступен, по имени диск бы не подключился.
* `/mnt/nfs` — стандартное место для временно/сетево монтируемых ФС.
* Тип `nfs`, опции `rw` — чтение-запись.
* Запись в fstab делает подключение **постоянным** (переживёт
  перезагрузку); `mount -a` монтирует прямо сейчас.
* `ls /mnt/nfs` — наглядно показывает файл `test`, созданный на сервере:
  если он виден, цепочка сервер → сеть → клиент работает.

Доступ к шаре у клиента есть именно потому, что HQ-SRV экспортирует её
для `192.168.200.0/29` — сети, где живёт этот узел.

## 5. SSH и `userssh`

Полностью совпадает с HQ-SRV/BR-SRV ([05-hq-srv.md §3](05-hq-srv.md#3-ssh-и-пользователь-userssh)):
UID 2027, wheel, sudo без пароля, порт 2127, root запрещён, `AllowUsers`,
`MaxAuthTries 2`, баннер.

**Зачем SSH на клиентской машине.** Он нужен двум автоматизированным
процессам:

* **Ansible** на BR-SRV управляет HQ-CLI как любым другим узлом;
* **`gost.sh`** на HQ-SRV копирует корневой сертификат УЦ на HQ-CLI через
  `scp -P 2127 … userssh@…`.

Оба находят HQ-CLI **сканированием пула DHCP на открытый порт 2127** —
поэтому единый порт для всех серверов и клиента здесь важен.

## 7. Проверки

| Проверка | Смысл |
|---|---|
| `Yandex Browser installed` → `rpm -q yandex-browser-stable` | пакет установлен (сейчас закомментирована вместе с установкой) |
| `/mnt/nfs is mounted` → `mountpoint -q` | NFS реально смонтирован, а не просто создан каталог |
| `NFS mount added to fstab` | подключение будет восстановлено после перезагрузки |
| chrony (4 проверки) | сервис, автозапуск, конфиг, реальная синхронизация с `172.16.1.1` |
| остальные | пользователь и SSH, как на серверах |
